# Домашнее задание к семинару 3. Полигон 3

**Приём открыт. Срок сдачи: 29.11.2026, 23:59 МСК.**

Напишите программу, которая подбирает закупку и доставку по заявке заказчика.
Стенд запускает её в трёх отдельных процессах: координатор получает заявку,
снабжение получает предложения поставщиков, а логистика получает расписание
рейсов. У каждой роли свои документы и память. Чтобы составить общий план,
роли обмениваются сообщениями.

Координатор должен сдать план, который выполняет всю заявку и соблюдает
ограничения по товарам, количеству, перевозке, срокам и бюджету. Если допустимого
плана нет, он может отправить ответ `infeasible`; сервер проверит, действительно
ли задача не имеет решения.

## Что нужно сдать

Загрузите один Python-файл с функцией:

```python
def act(observation, memory):
    # Выберите действие и обновите память текущей роли.
    return action, memory
```

В заготовке функция уже определена. Рабочий файл находится в
`polygon3/negotiation_agent.py`. Все локальные команды ниже выполняются из
корня `llmtik-seminars/seminars`. Требуется Python 3.11 или новее.
Сторонние пакеты для локальной проверки не нужны.

Стенд загружает один и тот же файл в каждый из трёх процессов. Функция узнаёт
свою роль из `observation["role"]` и получает результат предыдущего собственного
действия в `observation["last_result"]`. В `memory` хранится JSON-совместимая
память этой роли; она не является общим словарём команды.

В отправку входит только выбранный Python-файл. Ваши локальные тесты,
`negotiation_probe.py` и другие файлы из папки вместе с ним не загружаются.
Прежние `polygon3/agent.py`, `polygon2/agent.py` и свои старые тесты можно
сохранить без изменений.

## Данные ролей

| Роль | Какие документы она получает |
|---|---|
| `coordinator` | Заявку: товары, количества, разрешённые замены, обязательные свойства, адрес, бюджет и срок доставки. |
| `supply` | Предложения поставщиков: товары, склады, цены, остатки, минимальные партии, упаковки и время готовности. |
| `logistics` | Рейсы: склады отправления, адреса доставки, расписание, вместимость, допустимые категории груза и стоимость перевозки. |

Роль читает свой документ командой `read`. Сведения из документов других ролей
она получает через `send`. Доступ к чужим документам через `read` запрещён.
Отправителя сообщения указывает среда в поле `from`; запись `body.role` или
`body.from` не меняет отправителя.

Условия записаны в текстах документов. Команда `model` позволяет извлечь их
в нужную структуру. Код программы выбирает действия, обрабатывает ответы,
проверяет условия и собирает итоговый план.

## Условия допустимого плана

В заявке от одной до трёх строк. Для каждой строки нужно выбрать одно
предложение поставщика и один прямой рейс. Количество должно точно совпасть
с заявкой. Делить строку между поставщиками, закупать лишнее или использовать
пересадки нельзя.

План должен удовлетворять следующим условиям:

- Товар соответствует `sku` из заявки или входит в её список `allowed_skus`.
  Все `required_properties` обязательны, в том числе для исходного товара.
- Если несколько строк используют один `offer_id`, их количества складываются.
  Сумма не превышает запас, достигает минимальной партии и кратна упаковке.
- Склад поставщика совпадает со складом отправления рейса, а адрес рейса
  совпадает с адресом доставки из заявки.
- Товар готов не позже отправления, а рейс прибывает не позже срока заявки.
  Равенство допустимо в обоих случаях. Прибытие не предшествует отправлению.
- Если несколько строк едут одним рейсом, складывается их масса. Общая масса
  не превышает вместимость. Рейс принимает все категории груза, указанные
  и в заявке, и у выбранных товаров.
- Общая стоимость включает товары, обязательные платежи поставщиков и рейсы.
  Платёж каждого использованного предложения и каждого рейса учитывается один
  раз. Общая сумма не превышает бюджет заявки.

Количество, массу, денежные суммы и время указывайте целыми числами.
Количество измеряется в штуках, масса измеряется в граммах, деньги измеряются
в копейках, время измеряется в минутах после 09:00. Значения `true` и `false`
не принимаются вместо чисел.

Самый дешёвый план искать необязательно: основной балл зависит от допустимости
решения. Стоимость и разница с оптимальной стоимостью выводятся отдельно.

## Действия и итоговый ответ

Функция `act` возвращает одно действие за вызов.

| Действие | Формат и результат |
|---|---|
| Прочитать свой документ | `{"type": "read", "doc_id": "D1"}` возвращает документ в `last_result`. Идентификатор нужно взять из `observation["documents"]`. |
| Отправить сообщение | `{"type": "send", "to": "supply", "body": {...}}` передаёт сообщение выбранной роли. Входящие находятся в `observation["messages"]`. |
| Дождаться следующего хода | `{"type": "wait"}` завершает текущий ход без отправки сообщения. |
| Извлечь данные моделью | `{"type": "model", "system": "...", "messages": [{"role": "user", "content": "..."}], "max_tokens": 1024}` возвращает ответ через `last_result`. |
| Сдать решение | `{"type": "submit", "epoch": 1, "plan": {...}}` завершает эпизод и передаёт план на внешнюю проверку. Действие доступно координатору. |
| Остановиться без решения | `{"type": "stop", "reason": "..."}` завершает неполный поиск координатора. Такое завершение не засчитывается как решённый случай. |

Пример формата плана для заявки из одной строки:

```json
{
  "status": "feasible",
  "lines": [
    {"line_id": "L1", "offer_id": "O1", "trip_id": "T1", "quantity": 2}
  ]
}
```

Значения в примере показывают только формат. В своей программе используйте
идентификаторы и количества из текущего случая. В плане должны присутствовать
все строки заявки. Дополнительные поля с объяснениями, стоимостью или ролью
в итоговый объект не входят.

Если программа установила, что допустимого плана нет, формат ответа такой:

```json
{"status": "infeasible"}
```

Отказ одного поставщика, отсутствие подходящей локальной альтернативы или
исчерпание числа попыток сами по себе не означают, что задача не имеет решения.
Сервер сверяет `infeasible` с результатом полного поиска. Ответ `stop` и
неподтверждённое утверждение о невозможности получают ноль за случай.

## Изменение документов и обработка сообщений

Во время эпизода документы могут обновляться. Поле `epoch` показывает текущую
редакцию условий. После её изменения нужно перечитать затронутые данные и
проверить решение заново. Результат извлечения из старого документа нельзя
считать данными новой редакции.

При `submit` укажите текущий `epoch`. Если он устарел, среда вернёт
`stale_epoch`, а эпизод продолжится.

Номер сообщения `id` и номер предложения `proposal_id` используются для
разных проверок. По `id` можно исключить повторную обработку сообщения.
По ключу предложения можно определить, к какому варианту относится ответ.
Сообщение с меньшим `id` может прийти позже; повтор ответа одной роли не
заменяет ответ другой роли.

## Проверка на своём компьютере

Сначала сохраните исходную программу. Если такой файл уже существует,
выберите новое имя, чтобы не потерять свою работу.

```bash
python -m polygon3 snapshot --agent polygon3/negotiation_agent.py --output artifacts/polygon3/negotiation/start.py
```

Проверьте программу на открытом случае:

```bash
python -m polygon3.negotiation_probe --case case_001 --agent polygon3/negotiation_agent.py --output artifacts/polygon3/negotiation/start_001.json
```

```bash
python -m polygon3.negotiation_probe --case case_020 --agent polygon3/negotiation_agent.py --output artifacts/polygon3/negotiation/start_020.json
```

Эти команды используют `scripted`: вместо запроса к живой модели обработчик
возвращает точные факты текущей роли. Вызовы команды `model` учитываются в
бюджете, но HTTP-запросов к модели нет. Так можно проверить управление
программой отдельно от извлечения текста. Качество промптов этот режим не
проверяет.

Заготовка содержит ошибки, которые разбираются на практике. Сохраните исходный
отчёт, затем сравните его с отчётом после исправления. Последовательность
работы и задания находятся в [практика.md](практика.md). В файле
`polygon3/negotiation_test_support.py` предоставлены данные и функции для
локальных тестов; рабочий агент не должен зависеть от этого модуля.

Общий CLI позволяет сравнить две версии на одинаковых входах:

```bash
python -m polygon3 compare --a artifacts/polygon3/negotiation/start.py --b polygon3/negotiation_agent.py --cases case_001,case_020 --model scripted --calls 9 --output artifacts/polygon3/negotiation/compare.json
```

Локальные запуски не отправляют решение на стенд и не расходуют попытки сдачи.
Открытые файлы случаев доступны вам для изучения. Режим `development` запускает
отдельные процессы, но на macOS не обеспечивает строгую изоляцию неизвестного
чужого кода. Используйте его для своей программы. На сервере применяется
строгая Linux-изоляция.

## Протокол, который разбирается на практике

В заготовке координатор запрашивает рекомендации, собирает предложение и
передаёт его снабжению и логистике. Каждая роль проверяет свою часть и отвечает
`approve` или `reject`. Отказ содержит причину и локальную альтернативу, если
она найдена. Роли передают рекомендации и условия выбранных позиций; полные
каталоги для централизованного перебора в этом упражнении не пересылаются.

Поле `epoch` указывает редакцию условий, `proposal_id` указывает номер
предложения, а `digest` вычисляется из всего его содержания и позволяет
проверить, что оно не изменилось. При замене товара, рейса или другого условия
координатор создаёт новое предложение и получает оба подтверждения заново. Код должен обрабатывать
повторные и запоздалые ответы, прекращать повтор одного и того же кандидата
и останавливаться, если продолжить поиск не удалось.

В заготовке уже есть чтение документов, извлечение фактов, арифметические
проверки и вычисление отпечатка. На практике вы дописываете обработку ответов,
пересмотр предложения, проверку подтверждений, сброс при обновлении и обработку
доставки. Собственные тесты проверяют эти изменения.

Отчёт `negotiation_probe` содержит две оценки:

- Внешняя проверка определяет, допустим ли план по условиям случая.
- `protocol_audit` проверяет, были ли предложение и соответствующие ответы
  доставлены до сдачи. Его результат не подтверждает правильность извлечённых
  фактов и арифметики.

В режиме переговоров команда возвращает код 0 только при правильном внешнем
результате, завершённом согласовании и успешном техническом выполнении.
При ожидаемой ошибке теста или неполном исходе код может быть ненулевым;
подробности остаются в сохранённом JSON. Общий `compare` оценивает внешний
результат и не выполняет переговорный аудит.

Чтобы проверить потерю подтверждения, сначала выполните обычный запуск
на том же случае и той же версии, затем добавьте воздействие:

```bash
python -m polygon3.negotiation_probe --case case_001 --agent polygon3/negotiation_agent.py --fault drop-approve --output artifacts/polygon3/negotiation/drop_approve.json
```

Также доступны `duplicate`, `reverse` и `late-approve`. Эти воздействия
изменяют доставку только в учебном запуске. Старые `no-feedback` и `drop-field`
из общего CLI рассчитаны на другой формат сообщений и не проверяют потерю
нового `approve`.

Стенд считает основной балл по итоговому ответу среды. Наличие двух `approve`
не является дополнительным серверным условием для начисления этого балла.

## Ресурсные ограничения

Пределы общие для трёх ролей в одном эпизоде:

| Ресурс | Предел |
|---|---:|
| Вызовы модели | 9 |
| Действия программы | 120 |
| Межролевые сообщения | 24 |
| Тело одного сообщения | 4096 байт |
| Все сообщения вместе | 32 КиБ |

Ответ модели ограничен 1024 токенами. Запрос к модели содержит не больше
32 элементов `messages` и занимает не больше 65 536 байт с полями транспорта.
Системное сообщение передаётся отдельным полем `system`; в `messages`
используются роли `user` и `assistant`.

На стенде модель работает через API курса. Общий лимит группы составляет
30 запросов в минуту. Дополнительный ключ провайдера не нужен.

Для проверки извлечения на живой модели используйте общий CLI с
`--model live`. Клиент берёт `POLYGON_TOKEN` из окружения или из `.env` рядом
с пакетом либо в корне `seminars`; значение окружения имеет приоритет.
Храните свой выданный токен отдельно от кода и не добавляйте `.env` в репозиторий.
Локальные проверки `scripted` токена не требуют.

## Отправка на стенд

Отправьте рабочий файл:

```bash
python -m polygon3 upload --agent polygon3/negotiation_agent.py --confirm
```

Команда напечатает номер прогона. Результат появится по адресу
`https://lectures.ai.dscs.pro/run/НОМЕР_ПРОГОНА`.
В этом туре разрешены две отправки за день по Москве.
Счётчик обнуляется в 00:00 МСК.
После срока сдачи сервер отклоняет студенческие отправки с HTTP 403.

## Как считается результат

В табличном прогоне восемь скрытых случаев. Случай засчитывается, если
координатор сдал полный допустимый план или правильный ответ `infeasible`.
Неверный план, ложное утверждение о невозможности и неполное завершение
получают ноль. Частичных баллов за отдельные строки заявки нет.

```text
Баллы стенда = 100 × число засчитанных случаев / 8
```

Один засчитанный случай даёт 12,5 балла, четыре дают 50, все восемь дают 100.
Это результат программы на стенде, а не итоговая оценка за курс.
Контрольная команда с полным сбором сведений получила 87,5 балла, решив 7 из 8
случаев. Этот результат показан отдельной строкой в таблице и не занимает места.
Проходной порог для этого задания пока не объявлен.

После срока сдачи предусмотрена отдельная проверка лучших отправок на закрытом
итоговом наборе. Этот набор не входит в локальную раздачу.
