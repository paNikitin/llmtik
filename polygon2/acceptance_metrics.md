## Что считали

### Определения

- **Код-вариант** — модуль, претендующий на роль решения задачи (файл `target` из `task.json`).
- **Принят** — прогон тестов дал `report["ok"] is True`, `tests["ran"] > 0`, `tests["passed"] == tests["ran"]` и пустой `tests["import_errors"]`. Это в точности предикат `engine.checks._passed_all`.
- **t** — доля принятых среди правильных вариантов (10 эталонов).
- **f** — доля принятых среди неправильных вариантов; чем выше f, тем хуже тесты отсеивают неверный код. Эквивалентные мутанты в знаменатель f не входят.

### Состав корпуса

- Правильные варианты: `tasks/train/<task>/reference/<target>`, по одному на каждую из 10 задач.
- Неправильные варианты, 36 штук:
  - 7 задач fix/implement — исходный `tasks/train/<task>/workspace/<target>`;
  - 3 задачи tests — неэквивалентные мутанты: t03 — M1–M8 (8), t09 — M1–M10 (10), t10 — M1–M11 (11), всего 29.
- Эквивалентные мутанты, 3 штуки: t03/M9, t09/M11, t10/M12. Посчитаны отдельно и в f не включены.

Число тестов при эталоне: t01 — 3, t02 — 2, t03 — 7, t04 — 4, t05 — 4, t06 — 4, t07 — 2, t08 — 2, t09 — 13, t10 — 15.

### Метод запуска

Использовался штатный движок набора, а не прямой вызов `unittest`:

- интерпретатор — `../.venv/bin/python` (Python 3.13.9);
- задача загружалась через `engine.workspace.load_task("tasks/train/<task>")`;
- запуск — `engine.local.SubprocessHarness(env=dict(os.environ, POLYGON_SANDBOX_LANDLOCK="off"))`, режим `"tests"`;
- файлы — `files = dict(task.files)`, затем `files[task.target] = <исходник варианта>`;
- для fix/implement `args` — все пути из `visible_tests` (`tests/test_*.py`);
- для tests в `files[task.tests_path]` подставлялся `tests_reference.py`, `args = [task.tests_path]`;
- вердикт выносился по `report["tests"]` (`ran`, `passed`, `import_errors`) и `report["ok"]`.

Все 49 прогонов (10 эталонов + 36 неправильных + 3 эквивалентных) завершились с `ok=True`; ошибок импорта и таймаутов не было. Для справки тем же движком отдельно прогнаны скрытые проверки fix/implement-задач (режим `checks`), они в t и f не входят.

### Контроль методики

- Все 10 эталонов приняты: `ok=True`, `passed == ran` (3, 2, 7, 4, 4, 4, 2, 2, 13, 15), `import_errors` пуст. Исходная методика правки не потребовала.
- Для задач tests дополнительно выполнен прогон с переписыванием исходника через `engine.checks.disguise` (как в оценщике). Классификация всех эталонов и мутантов совпала с обычным прогоном, расхождений нет.

### Допущения и ограничения

- Принятие fix/implement определяется **только видимыми тестами**, как задано в условии. Видимые тесты не покрывают все требования: t04, t05 и t06 проходят их, но проваливают скрытые FAIL_TO_PASS (0/6, 0/4, 0/4). Именно поэтому f для fix равен 100%.
- **Особенность t01:** в рабочей копии `workspace/stock.py` побайтно совпадает с `reference/stock.py` (MD5 `2906de7ffa21bf491642cc77862437b5`): относительно HEAD в файле есть незакоммитленная правка (`reverse=True` убран из `consume`). Это не влияет на метрику: версия из HEAD с багом (`reverse=True`) также проходит все 3 видимых теста (при скрытых FAIL_TO_PASS 0/2, PASS_TO_PASS 7/7). То есть t01 принимается при обоих состояниях файла, потому что видимые тесты не проверяют порядок списания партий. t01 обоснованно остаётся в знаменателе f, корректировка не требуется.
- Эквивалентность мутантов принималась по меткам `mutants.json`; отдельной проверки эквивалентности не проводилось. Все три таких мутанта эталонные тесты принимают, что согласуется с метками.
- Метрика отражает только данный корпус из 10 задач и данный набор тестов; она не является оценкой качества тестов за его пределами.
- Настоящее измерение не изменяло файлы репозитория; временные скрипты выполнялись вне репозитория и удалены.
