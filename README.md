## C4 v3: версии событий и размер состояния

Программа получает состояние рынка и сообщения, а затем возвращает три действия:
`order_raw`, `produce`, `price`. Числовая политика уже написана. В задании нужно
преобразовать сообщения в версии событий, сохранить их в `memory` и восстановить
текущее состояние при любом порядке доставки.

Версия 3 использует тот же рынок `market_v2.py` и те же сообщения, что версия 2.
Изменились правила хранения состояния и подсчёт баллов. Перед каждым вызовом
`act` модуль агента загружается заново. Между вызовами сохраняется только
JSON-словарь `memory`. Его размер проверяется после каждого `act`, до шага рынка,
включая последний день эпизода.

В `solution.py` оставлены шесть функций с пометкой `TODO`:

1. `build_context(memory, text)`;
2. `build_prompt(text, context)`;
3. `parse_response(raw)`;
4. `validate_patch(data)`;
5. `apply_patch(patch, memory)`;
6. `active_events(memory, day)`.

`act`, обращение к модели, расчёт ожидаемого спроса и числовая политика готовы.
Не меняйте контракт результата `act`.

## Контракт одной версии

Модель возвращает один JSON-объект с точными верхними полями:

```text
event_id, revision, operation, issued_day, fields
```

Правила:

- `event_id` — непустая строка;
- `revision` — целое число без подмены логическим значением;
- `operation` — `create`, `update` или `cancel`;
- `issued_day` — абсолютный целый день от 0;
- `create` разрешён только для ревизии 1;
- `update` и `cancel` начинаются с ревизии 2;
- `fields` содержит только `direction`, `start`, `length`, `factor`;
- неизвестное поле отсутствует; значения `null` и 0 вместо неизвестного не подходят;
- `direction` равен `up` или `down`;
- `start` — абсолютный целый день от 0;
- `length` — положительное целое число;
- `factor` — конечное положительное число;
- у `cancel` поле `fields` пустое.

`direction` необязателен для готового события. Если он есть, `up` согласуется с
`factor > 1`, `down` — с `0 < factor < 1`. Значение `factor == 1` допускается
только без `direction`.

Ответ разбирается целиком. Пояснение вокруг JSON и блок Markdown не считаются
частью контракта. Если обязательные метаданные версии или ссылка на прежнее
событие неоднозначны, ответ можно представить как JSON `null`. Такой ответ не
надо сохранять в словаре ответов.

## Память и воспроизведение журнала

Вся информация между вызовами хранится в переданном `memory`. Допускаются только
JSON-значения: словари со строковыми ключами, списки, строки, конечные числа,
логические значения и `null`. Множества, кортежи, объекты Python, `NaN` и
бесконечности не допускаются. Состояние модуля между вызовами использовать нельзя.
Готовая обвязка создаёт такую основу:

```text
patch_journal  список принятых версий
event_state    восстановленное состояние по event_id
responses      ответы модели по тексту и сводке памяти
news_history   несколько последних сообщений
errors         причины пропусков
current_day    текущий абсолютный день
```

`apply_patch` сохраняет журнал и каждый раз воспроизводит версии события по
возрастанию `revision`. Версия может прийти раньше предыдущей. Точный повтор не
увеличивает журнал. Другой объект с теми же `event_id` и `revision` — конфликт:
его нельзя считать последней истиной. Сохраните причину в `errors`.

Отмена окончательна. Более поздний `update`, а также поздно доставленные старые
`create` и `update` не возвращают отменённое событие.

`active_events(memory, day)` возвращает как текущие, так и будущие события. Это
нужно, чтобы заказать сырьё заранее. Событие попадает в результат, если в
журнале есть `create`, известны `start`, `length`, `factor`, оно не отменено и
ещё не истекло. Условие истечения: `start + length <= day`.

## Размер состояния и баллы v3

Размер — число байтов UTF-8 в строгом JSON-представлении всего `memory`, а не
объём оперативной памяти Python. Общий модуль `memory_policy.py` использует
`ensure_ascii=False`, `separators=(",", ":")`, `sort_keys=True`, `allow_nan=False`.
Кириллица измеряется в байтах UTF-8, не в символах. Размер возвращает
`memory_size(memory)`; функция `memory_penalty(size)` проверяет предел и
возвращает фиксированное списание.

| Максимальный размер JSON-состояния за весь прогон | Списание, баллы |
| --- | ---: |
| До 8 КиБ включительно (8192 байта) | 0 |
| Больше 8, до 16 КиБ включительно (16384 байта) | 10 |
| Больше 16, до 32 КиБ включительно (32768 байт) | 30 |
| Больше 32, до 64 КиБ включительно (65536 байт) | 70 |
| Больше 64 КиБ | Прогон не принимается |

За полный прогон берётся один наибольший размер после любого действия во всех
пяти эпизодах. Списание применяется **один раз к итоговым баллам**, а не к
каждому эпизоду и не к среднему размеру памяти:

```text
mean_profit = sum(profits) / len(profits)
raw_total = round(mean_profit / 1000, 2)
total = round(mean_profit / 1000 - memory_penalty(state_peak_bytes), 2)
```

Отрицательная прибыль и отрицательный итог сохраняются; ограничения снизу нулём
нет. Например, при баллах за прибыль −5 и списании 10 итог равен −15. Состояние,
превысившее 64 КиБ хотя бы после одного действия, нельзя сделать допустимым
позднейшим уменьшением словаря.

Ограничивайте не только контекст модели, но и сохранённые ответы, историю и
список ошибок. При сокращении журнала нельзя терять сведения, нужные для
поздних ревизий, повторов и окончательной отмены.

Сервер отдельно контролирует RSS процесса: предел — 128 МиБ. Это не размер
JSON-состояния и не основа для списания баллов. Локальная проверка ограничивает
JSON-состояние, но не обещает контроль RSS на macOS или полную изоляцию процесса.
Полный JSON-ответ обмена, содержащий действие и память, ограничен 256 КиБ
(262144 байта с завершающим переводом строки).

## Контекст модели

Следующее сообщение может ссылаться на прежнее. Например, перенос на два дня
позже требует известного `start` и должен дать новый абсолютный `start`.
`build_context` поэтому включает восстановленные поля, идентификаторы и номера
ревизий, а также несколько последних сообщений. Ограничьте число событий,
сообщений и длину текста константами из файла.

Словарь ответов нельзя ключевать только исходным текстом: одинаковый текст при
другом состоянии может означать другую ссылку. Готовая функция `_context_key`
использует и текст, и сводку памяти.

В `events_examples.json` находятся восемь синтетических сообщений с частичным
созданием, относительным переносом, отменой и доставкой не по порядку. Это не
сообщения скрытой среды.

## Проверка без сети

Нужен Python 3.10 или новее. Зависимости транспорта:

```bash
python -m pip install -r requirements.txt
```

Для прогона учебной среды выполните `python solution.py`. Без токена и до
заполнения TODO работает готовый числовой вариант. По умолчанию используется
версия 3: локальный клиент заново импортирует модуль перед каждым `act`, передаёт
память через JSON и проверяет её размер до шага рынка.

Готовая часть должна проходить до заполнения `TODO`:

```bash
python -m unittest test_solution.ReadyCodeTests test_client -v
```

Учебные проверки сначала будут завершаться ошибками `TODO`:

```bash
python -m unittest test_solution.ExerciseTests -v
```

После реализации запустите весь набор:

```bash
python -m unittest test_solution test_client -v
```

Тесты подменяют SDK и HTTP, не выполняют сетевых запросов и не читают настоящий
`.env`. Для отдельной самопроверки:

```python
from polygon import self_check
from solution import act

result = self_check(act)  # пять учебных эпизодов по правилам v3
print(result["raw_total"])         # баллы за прибыль без списания
print(result["state_peak_bytes"])  # пик JSON-состояния за все эпизоды
print(result["memory_penalty"])    # одно фиксированное списание
print(result["total"])             # итоговые баллы
```

В результате также есть `profit` (округлённая средняя прибыль) и `episodes`.
`local_episode(act)` по-прежнему возвращает прибыль одного эпизода числом;
`local_episode(act, verbose=True)` отдельно показывает его баллы, размер
состояния и списание. Учебные эпизоды не предсказывают результат скрытого прогона.

## Обращение к модели

Скопируйте `.env.example` в `.env`, если локального файла ещё нет, и заполните
`POLYGON_TOKEN` своим токеном Полигона. Для обращения к модели и отправки решения
используется **один и тот же токен**. Клиент читает его и `POLYGON_URL` из
окружения или из `.env` рядом с файлами решения. `.env` исключён из Git;
в шаблоне токен пустой. Не вставляйте токен в `solution.py`, отчёт или чат.

Используется официальный `anthropic` SDK и маршрут Messages API `/v1/messages`.
Модель — `deepseek-flash`; рассуждение отключено, температура передаётся через
`extra_body`. Общий лимит группы — 30 запросов в минуту, не отдельный лимит на
каждого участника. Клиент не повторяет HTTP 429 автоматически и показывает
`Retry-After` без токена.

Перед отправкой проведите собственный опыт на нескольких последовательностях
из `events_examples.json`: поменяйте порядок доставки, добавьте точный повтор и
сравните `patch_journal`, `event_state`, `active_events`. Проверьте также размер
состояния после каждого действия. Сначала сохраните наблюдение и найденную
ошибку, затем открывайте таблицу результатов. Для c4 доступно пять отправок за
24 часа.

## Отправка и совместимость

После локальной проверки:

```python
from polygon import submit

submit('solution.py', challenge='c4')  # rules_version=3 по умолчанию
```

Перед отправкой клиент запрашивает `/health` и проверяет, что сервер принимает
выбранную версию. При несовпадении версии файл не отправляется. Для c5 и c6
версия по умолчанию остаётся 1.

Старые результаты сохраняются в личной истории и не смешиваются с текущими.
На сайте открыта только таблица активной версии. Старые правила можно явно
выбрать для локального воспроизведения:

```python
from polygon import local_episode, self_check

local_episode(act, rules_version=1)
local_episode(act, rules_version=2)
self_check(act, rules_version=2)  # прежнее возвращаемое значение: средняя прибыль
```

В v1 нет перезапуска модуля; в v2 он выполняется в предусмотренные средой дни.
Эти версии не используют новое списание за размер состояния. Явная отправка
`rules_version=1` или `2` возможна только на сервер, принимающий эту версию;
проверка `/health` не позволяет отправить её на действующий тур v3.
